# 新版图 (d)：六请求到达、入池、批处理与输出全过程

[单独查看图 (d)](pdblend-multi-request-detail.png) · [矢量 SVG](pdblend-multi-request-detail.svg) · [矢量 PDF](pdblend-multi-request-detail.pdf) · [完整 (a)–(d)](pdblend-online-scheduling.png)

这个例子把六个请求放在**同一条时间轴**上，展示请求到达后进入哪个池、绑定哪些实例、在哪里等待、如何与已有请求合并 batch，以及每个输出 token 来自哪个实例。图中的 0…14 是逻辑时隙，不是秒或毫秒，也不是性能模拟结果。路由所需的安全候选集合与预计 TTFT 排序是明确给定的示意条件，未调用实际 profile 声称这些数值已通过预测。

## 1. 初始状态与例子假设

- 固定角色池：M0、M1、M2、M3，以及兼容的 P0、D0。图展开 M0、M1、P0、D0。
- M2、M3 有已有背景工作，在此示例每次决策中预计 TTFT 较差；“忙”不等于不能接收请求，它们仍参与路由候选比较。
- 阈值 `τ=1024`；SLO routing 开启；角色、频率在这个短示例内不变。
- R2、R4 的 PD 预测在包含 P 排队后仍安全，容量也足够。
- R5 加到 M0、R6 加到 M1 时，均通过容量、该请求的 SLO 和已有请求延迟预算检查，并在安全候选中预计 TTFT 最小。
- R6 的 K=2；此例没有 PD 两 token first-gap 测量预测覆盖，但有安全 M1 预测，因此发生 PD→M。**不是所有 K=2 请求必走 M，也不是缺 PD 预测必然转 M。**若没有安全 M，代码可能保留容量允许的 PD，标记 SLO 未证实。
- 每个请求均输出完整 K 个 token；没有提前 EOS。所有 token 均以 `y1…yK` 编号，前面的 R 编号区分不同请求。

## 2. 六次到达与最终 assignment

| 请求 | 到达 | 输入 L | 输出 K | 长度判定 | 最终 prefill / decode | 选择理由 |
|---|---:|---:|---:|---|---|---|
| R1 | 0 | 256 | 8 | M | M0 / M0 | M0 是安全 M 候选中预计 TTFT 最小者 |
| R2 | 1 | 2048 | 6 | PD | P0 / D0 | P/D 兼容、容量和预测通过 |
| R3 | 2 | 512 | 5 | M | M1 / M1 | 此时 M1 的预计 TTFT 最小 |
| R4 | 3 | 3072 | 5 | PD | P0 / D0 | 虽需等 P0，包含等待后的预测仍安全；到达时就绑定 D0 |
| R5 | 4 | 256 | 4 | M | M0 / M0 | 加入后仍保护 R1 的预算，且 M0 预计 TTFT 最小 |
| R6 | 5 | 2048 | 2 | PD | M1 / M1 | PD first-gap 预测缺覆盖，但 M1 安全且最优，派发前改为 M |

R1/R3/R5 按长度进入 Mixed，R2/R4 按长度进入 PD。R6 展示同一次请求选择中“先得到 PD 候选分支，再经 SLO 层改选 M”的过程；R6 从未在 P0/D0 实际运行，不是运行中的请求迁移。

## 3. Mixed 池的实际调度

**M0 执行 R1、R5。**

| 区间 | 同一 M0 batch 中的工作 | 区间结束时的输出 |
|---|---|---|
| [0,2) | R1 prefill | @2：R1 y1 |
| [2,4) | R1 decode | @3：R1 y2；@4：R1 y3 |
| [4,6) | R1 decode + R5 prefill chunks | @5：R1 y4；@6：R1 y5、R5 y1 |
| [6,9) | R1 decode + R5 decode | @7/8/9：两请求各产生一个 token |
| @9 | R1、R5 均完成 | R1 共 8，R5 共 4 |

R5 在 4 到达时，R1 还在 decode。引擎可以用同一个 batch 推进 R1 的 decode 和 R5 的 prefill。图中上下两条请求行在同一列的色块表示**一次 batch 中的多请求工作**，不是同一 GPU 上两个独立执行流。

**M1 执行 R3、R6。**

| 区间 | 同一 M1 batch 中的工作 | 区间结束时的输出 |
|---|---|---|
| [2,4) | R3 prefill | @4：R3 y1 |
| [4,5) | R3 decode | @5：R3 y2 |
| [5,8) | R3 decode + R6 prefill chunks | @6/7/8：R3 y3/y4/y5，随后 R3 完成 |
| [8,9) | R6 剩余 prefill | @9：R6 y1 |
| [9,10) | R6 本地 decode | @10：R6 y2，完成 |

R6 只在 M1 上产生两个 token，没有远程 KV handoff。

## 4. PD 池的实际调度

**P0 的 prompt 阶段：**

1. R2 在 1 到达，立即绑定 `(P0,D0)`，P0 在 `[1,5)` 处理 prompt，@5 产生并向客户端返回 R2 y1。
2. R4 在 3 到达，也立即绑定 `(P0,D0)`。此时本例 P0 的可用调度预算已被前序工作占用，所以 R4 在 `[3,5)` 等待。这个等待不意味着 P 实例的实现永远串行处理 prompt。
3. P0 在 `[5,9)` 处理 R4，@9 返回 R4 y1。

**KV 与 D0 的后续阶段：**

- R2 的 prompt KV 在示意的 `[4,5)` 逐层传递，可与 prefill 尾部重叠。P 首 token @5 后，D 请求在 handoff/接纳等待后于 6 开始首个 decode step，@7 得到 R2 y2。
- R4 的 prompt KV 在示意的 `[8,9)` 传递；y1 @9 后，D0 于 10 开始首个 decode step，@11 得到 R4 y2。
- D0 在 `[6,10)` 推进 R2；在 `[10,11)` 将 R2、R4 放入同一个 decode batch，@11 同时得到 R2 y6 和 R4 y2。
- R2 @11 完成；D0 继续 R4，@12/13/14 得到 y3/y4/y5，@14 完成。

这里同时体现两种并行：`[6,9)` 中 P0 计算 R4 的 prefill、D0 计算 R2 的 decode；`[10,11)` 中同一个 D0 batch 推进 R2、R4 两条 decode。

**P0 总共只输出 2 个首 token，D0 输出余下 9 个 token。**D0 的第一步输入是所携带的 y1，并复用原 prompt 的 KV，不重新完整 prefill 原 prompt。

## 5. 每条请求完整的 token 时间表

| 请求 | 首 token：时刻 / 实例 | 后续 token 时刻 / 实例 | 总数 |
|---|---|---|---:|
| R1 | y1 @2 / M0 | y2…y8 @3…9 / M0 | 8 |
| R2 | y1 @5 / P0 | y2…y6 @7…11 / D0 | 6 |
| R3 | y1 @4 / M1 | y2…y5 @5…8 / M1 | 5 |
| R4 | y1 @9 / P0 | y2…y5 @11…14 / D0 | 5 |
| R5 | y1 @6 / M0 | y2…y4 @7…9 / M0 | 4 |
| R6 | y1 @9 / M1 | y2 @10 / M1 | 2 |

黄色 token 一共 30 个；其中 Mixed 产生 19 个，PD 路径产生 11 个。R2 的 TTFT 为逻辑区间 1→5、首 gap 为 5→7；R4 的 TTFT 为 3→9，包含 P 等待，首 gap 为 9→11。不能把这两个 gap 直接解释为纯 KV copy 时间。

## 6. 关键记账：D 先被 assign，后开始执行

以下仅统计六条示例请求，不含 M2/M3 的背景请求。

| 时刻 / 事件 | 代理记账变化 |
|---|---|
| 1：派发 R2 | `U_P0 += 2048`；`N_D0 = 1`，尽管 D0 尚未执行 R2 |
| 3：派发 R4 | `U_P0 = 5120`；`N_D0 = 2`，R4 还在 P waiting |
| 5：R2 首 token | `U_P0 = 3072`；`N_D0` 仍为 2 |
| 5：最终派发 R6 到 M1 | `U_M1 += 2048`、`N_M1 += 1`；不增加 P0/D0 记账 |
| 9：R4 首 token | `U_P0 = 0`；D0 仍拥有 R2/R4 两个未完成请求 |
| 11：R2 完成 | `N_D0 = 1` |
| 14：R4 完成 | `N_D0 = 0` |

U 是“尚未见首 token”的代理负载统计；清零不等于所有引擎 KV 所有权立即释放。图展示正常完成路径，失败与原生清理仍遵守完整说明中的 ownership 规则。

## 7. 文件与验证

六请求事件源在 [multi-request-scenario.json](multi-request-scenario.json)。生成器检查每条请求先到达再执行、首 token 对齐 prefill 结束、输出顺序及数量、PD KV/handoff 先于 D 首输出、M 请求不带远程 KV。已验证 6 条请求、30 个 token，并目视核对泳道与输出行。

三个 subagent 并行复核路由条件、实例批处理与适用边界。本轮更新的是论文机制图，未修改业务代码或运行 GPU 实验。
